# Participant availability collection — 5 November 2026

Owners can create separate candidate/interviewer capability links for an owned candidate/job, inspect response states, revoke both links, and propose common times from both current responses using the existing Google free/busy adapter and common-slot engine. The public `/availability` page needs no application account or Google login. The initial forms accept one window; the response API accepts up to 20. Links default to 48 hours (API 1–168 hours), with five correction submissions and revision checks.

Tokens use 32 random bytes and hashed storage, constant-time comparison and generic invalid-link errors. Tokens travel in a URL fragment, are removed from browser history after mount and are submitted only in POST bodies. They are not returned by list/read/respond endpoints or written to audits. Only owner creation discloses them once; lost links require revoking the request and creating another. Creation request identities are content-bound and retry-safe without redisclosing credentials. Exact response retries do not consume another correction; stale differing responses reject. No other participant's windows, candidate details or job details are returned publicly. Responses prove capability possession, not verified personal identity or interview acceptance. Links must not be forwarded.

Existing workspace transactions serialize responses, revocations and proposal revision checks. Withdrawal/do-not-contact stop flows invalidate links, while the existing candidate-erasure hook also redacts windows/timezone and destroys token hashes. Revoked/expired capabilities stop public access. Submitted times are retained for owner review until the existing erasure flow removes them; link expiry alone is not a data-retention purge.
