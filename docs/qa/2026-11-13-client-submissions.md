# Private client submissions and source-bound review

Date: 13 November 2026 (Asia/Calcutta). Scope: partial M17-F01/F02/F03/F04/F05/F06 and M24-F02. No entire advanced module is complete.

## Implemented behavior

- Owner `/submissions` prepares an immutable version from current structured candidate evidence. Fields are explicitly selected: skills, work models, locations and notice period. Names, direct contacts, raw CVs, compensation and private notes are excluded; direct contact patterns and the candidate name in selected strings are rejected. Exact candidate/job/client sharing consent, recorded field limits, fresh evidence, suppression, active role/company, permitted client contact and configured client mailbox are required. Source/pack fingerprints, version/hash, recipient, expiry and bounded transactional-code authority accompany one mandatory `candidate_share` approval. Retries reuse request identity and stale versions cannot create competing packs.
- Approval authorizes `release_ready`, with no invented `sharedAt`, `viewedAt` or access expiry. Explicit release of the exact approved pack creates a recipient-bound revocable fragment capability and sets `shared`/`sharedAt`; this means usable private access exists, not email delivery. Legacy shared/viewed statuses remain historical internal records and are not backfilled as authenticated outcomes. Governed packs block legacy state, note and generic approval bypasses. Company suppression now blocks canonical sharing eligibility as well.
- Private `/client-review` entry exposes only a masked recipient, version and expiry. It reveals no profile before email verification. The existing outbox queues a recipient-requested code under the exact owner-approved submission authority: at most three codes per recipient/day, one minute between new requests, ten-minute expiry, five failed guesses and single consumption. Canonical provider-accepted code delivery is required before verification. Short-lived sessions bind the exact version, recipient and active authority. Stable application secret/origin changes invalidate older authority. Raw codes and tokens are not persisted in normal message bodies; materialization occurs only at approved delivery.
- The existing email content hash, approval, dispatch, queue, recipient suppression, emergency stop, provider adapter, daily budget and uncertain-delivery reconciliation remain authoritative. Transactional security-code timing exceptions require the explicit bounded authority reviewed with the profile; campaign/invitation cadence retains normal quiet hours/contact spacing. Invitation mail needs its own canonical email approval. Source/recipient/version checks run at approval and final admission. Provider acceptance is separate from recipient delivery and authenticated profile serving.
- A private profile read is served only to a current verified-email session; this records `viewed` as authenticated profile serving, not proof of human attention. Job-specific clarification, interview interest, reviewed or non-progression observations are append-only with exact request identities, optimistic revisions and correction history. Email possession is verified; employer decision authority and exact candidate pack approval remain explicitly unverified. Feedback does not book an interview, progress/reject a candidate or bypass consequential approval.
- FU15 unviewed-review and FU16 feedback reminders reuse the existing engine, outbox and worker. A canonical sent invitation is required before chasing an earlier email. Current profile, recipient, sender, sharing/contact permission, authority and deadline are rechecked. Actual authenticated serving completes unviewed reminders; response completes feedback reminders. New versions, revoked access, suppressed/withdrawn candidates, changed recipients, cancelled jobs and expired consent stop unused work. Attempted/uncertain delivery remains in reconciliation instead of being erased or automatically resent.
- Canonical privacy fulfillment revokes private authority, sessions and unused client-thread messages/reminders before redacting historical packs, feedback, code/session events and request identities. No new document store, profile table, scheduler, sender or hiring-decision engine is created. Owner APIs and UI retain default owner-only workspace authorization; public mutations use private/no-store and no-referrer headers. Capabilities are removed from the visible URL and held in memory, not local storage.
