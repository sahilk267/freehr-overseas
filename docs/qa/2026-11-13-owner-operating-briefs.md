# Owner operating review and automatic internal briefs

Date: 13 November 2026 (Asia/Calcutta). Scope: partial M22-F01/F05 using existing M05 queue/worker, M23 analytics and owner controls. No entire advanced module is complete.

## Implemented behavior

- `/briefs` and `ownerBrief.*` are private owner-only workspace APIs. Current priorities read canonical pending approvals, blocked/permanently-failed/overdue tasks, stale worker leases, existing open incidents, due follow-up plans and recorded deadlines, collectible invoice balances and source-integrity issues. Deterministic priority and owner-configured attention hours guide review. Source age is not audited stage duration, and a review threshold is not a contractual SLA breach. Future-created rows appear as integrity concerns rather than fabricated waiting ages. Cases retain existing source IDs and route to the governing workspace; no second case, approval or decision engine is created. Several source records may describe one underlying business issue; no unique-issue total is inferred.
- Existing bounded source analytics supplies inventory, rolling period-created cohorts, exact currency-separated receipt/receivable totals, queue observations and unknown evidence. Filtering applies to the full supported source set before display pagination. Source limits fail closed instead of returning partial financial totals. Bank-cleared cash, measured margin/cost, factuality and effort saved remain unavailable. Current live pages are fresh snapshots, not a stable multi-page historical case export.
- Manual brief requests reuse exact request identity. Stored snapshots contain aggregate counts, observed workflow quantities, currency balances, fixed metric semantics and source hash commitments. People, source case IDs, message bodies, private notes, raw runtime errors and model identifiers are not copied into history. Decimal duration/latency and cohort-rate quantities serialize as fixed-precision decimal strings to avoid MySQL binary-floating-point round-trip drift; exact integer money remains unchanged. A canonical summary hash detects altered or inconsistent stored aggregates and tolerates JSON key reordering. This does not claim a tamper-proof audit system.
- Owner-configured opt-in daily/weekly schedules use explicit IANA timezone, local time, weekday, rolling review period, review threshold and 7–90-day retention. Default scheduling is off. Saving settings does not enable the managed worker or authorize recipient contact. Ambiguous/unavailable daylight-saving local times fail closed with a schedule record. One physical job and one summary per owner/calendar day are reused. Old periods are not backfilled using current outcomes. Early tasks defer to the actual approved instant; stale settings, elapsed periods, disabled workers and emergency stop prevent publication. Manual cancellation is respected until a new explicit owner configuration authorizes reuse.
- The existing managed worker polls scheduling and executes `owner_operating_brief` as a deterministic job independent of AI inference budget. The existing queue owns leases, concurrency, completion, blocked failures and retries. Its quota fallback queries deterministic work independently of the first 25 mixed tasks, so a full page of higher-priority AI tasks cannot starve this summary when the AI allowance is exhausted. Brief generation calls no external email/notification service, LLM or payment provider and does not approve/retry business cases, contact candidates/clients, modify policy, book interviews or make hiring decisions. The owner must use each governing workflow for those actions.
- History is private, hash checked and retention bounded. API reads hide expired summaries even when physical redaction is batched; up to 100 expired unredacted payloads are cleared per call, with a supported 10,000-row retention-source bound that fails closed for archival review. Current source rows remain canonical and are never deleted by brief retention. Settings preserve stale drafts and require explicit current-version review. Daily summaries are internal records available in the owner page; external push/email, audience distribution and complete SLA ladders are not implied. No new schema, API key, scheduler or provider credential is required.
