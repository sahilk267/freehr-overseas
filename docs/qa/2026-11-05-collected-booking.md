# Tentative booking from collected availability — 5 November 2026

Owners can review proposals from both submitted participant windows and save one tentative interview. Duration/buffer controls are available in the collection panel. Changing them clears old proposals. A saved proposal binds both response revisions and the selected Google calendar generation. Booking repeats the Google read before entering the shared workspace transaction, then checks current responses, expiry, candidate eligibility, calendar generation/check age, buffered candidate conflicts and active internal holds.

The canonical interview scheduler creates or reuses the interview, calendar UID, reminder configuration, audit and existing optional Calendar automation task. The same transaction records the request in the existing workflow ledger and closes both availability capabilities. No new schema, queue, cron or provider credentials are introduced. Concurrent requests cannot create duplicate interviews. Exact request replay returns the original interview even after cancellation/rescheduling; changed booking content for a consumed request is rejected. Final audit failure rolls back interview creation, ledger and token closure together.

The UI says **tentative booking**. This action does not prove participant identity/acceptance, send invitations or confirm an offer. Link possession remains the only assurance for submitted windows. Google free/busy is point-in-time, not a cross-provider reservation: an external calendar edit can race after a successful check. Google event creation/update follows the already-enabled Calendar automation policy and its conflict/retry controls. Existing internal holds are respected rather than silently consumed by an unrelated request. Confirmation/delivery, participant RSVP and automatic booking without owner review remain pending.
